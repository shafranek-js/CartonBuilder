# CartonBuilder 3D Rendering Research and Implementation Roadmap

## Executive recommendation

> **Wave 4 status (2026-08-03): Implemented in the current branch.** The
> packaging-finish milestone now carries finish roles and masks on artwork
> layers, composes PBR finish maps in Render, persists them through schema v10,
> and exports Full PBR GLB with a Basic Compatibility warning. The remaining
> production boundaries in this research document (CMYK/ICC/Pantone,
> separations, geometric displacement and path tracing) remain deferred.

CartonBuilder should evolve around a **dual-rendering strategy**:

**Technical Preview** should remain a fast, deterministic, color-neutral 3D inspection tool derived directly from the millimeter-based 2D carton model.

**Presentation Render** should become a separate, progressively enhanced workflow for producing attractive PNG, JPEG, and WebP mockups with controlled camera, lighting, materials, shadows, background, and optional depth of field.

The application should **not begin with full path tracing or a WebGPU rewrite**. The highest-value route is to improve the existing Three.js raster renderer first: correct color management, stronger camera and lighting presets, better carton geometry, adaptive anti-aliasing, ambient occlusion, offscreen high-resolution export, and transparent backgrounds. A path-traced still renderer should be evaluated only after that raster pipeline is stable.

This recommendation builds on the existing project architecture and the earlier research principle that the canonical carton and artwork model must remain millimeter-native and 2D-authoritative. The 3D view should always be derived from the flat net, including its panel UV coordinates and hinge relationships, rather than becoming a second source of truth. fileciteturn0file0 fileciteturn0file1

The current implementation is already significantly more advanced than a prototype. It uses Three.js `0.185.1`, lazy-loads the 3D module, constructs panels through a hinge graph, uses a single composed artwork texture, supports perspective and orthographic cameras, provides technical, studio, and photorealistic presets, handles WebGL context loss, disposes resources, and renders on demand. These are all sound architectural decisions and should be extended rather than replaced. fileciteturn5file0 fileciteturn7file0 fileciteturn9file0 fileciteturn10file0

A realistic delivery estimate for one experienced frontend/graphics developer is:

| Delivery level | Estimated effort | Product result |
|---|---:|---|
| Presentation Render MVP | 4–6 weeks | Transparent PNG, camera presets, lighting controls, stronger shadows, 2K/4K export |
| Production-quality raster renderer | 8–12 weeks | Improved geometry, materials, AO, settled-camera quality, adaptive performance |
| Full hardening and optional path-tracing prototype | 12–16 weeks | Device validation, visual regression suite, experimental progressive render |
| Production path-traced renderer | Additional 4–8 weeks | Optional high-quality still-render mode, subject to prototype results |

These estimates assume the current model, artwork editor, panel graph, and 3D implementation remain in place.

## Current renderer assessment

CartonBuilder’s existing `BoxScene` is based on `WebGLRenderer`, with antialiasing enabled, a device-pixel-ratio cap of two, sRGB output, one shadow-casting directional light, a hemisphere light, a `ShadowMaterial` ground plane, `CanvasTexture` artwork, anisotropic filtering, mipmapping, `RoomEnvironment`, PMREM-based image-based lighting, and material switching between `MeshBasicMaterial`, `MeshStandardMaterial`, and `MeshPhysicalMaterial`. fileciteturn9file0 fileciteturn10file0

The existing texture composer also contains several important production-oriented safeguards: a maximum texture edge of 4096 pixels, a maximum area of sixteen million pixels, a canvas fallback when `OffscreenCanvas` is unavailable, clipping to the panel union, panel-edge bleed, `createImageBitmap()` decoding, abort handling, and explicit bitmap disposal. fileciteturn11file0

### What is already correct

| Area | Existing implementation | Assessment |
|---|---|---|
| Source of truth | 3D is derived from `BoxNetModel` and artwork state | Correct |
| Folding | Rigid panel hierarchy with hinge pivots | Correct |
| UV workflow | One artwork texture derived from flat-net placement | Correct |
| Loading | 3D code is dynamically imported only when requested | Correct |
| Render scheduling | Rendering occurs on camera or state changes rather than continuously | Correct |
| Texture color space | Artwork texture is marked as `SRGBColorSpace` | Correct |
| Environment lighting | PMREM generated from `RoomEnvironment` | Correct |
| Resource cleanup | Textures, materials, geometry, controls, PMREM, and renderer are disposed | Correct |
| Recovery | WebGL context loss and restoration are handled | Correct |
| Accessibility | The 3D canvas is accompanied by DOM controls, summaries, and inspector state | Strong foundation |

Render-on-demand is particularly appropriate for product editors and viewers: the official Three.js guidance notes that continuously rendering an otherwise static scene wastes power and recommends requesting frames only when camera, data, textures, or controls change. CartonBuilder already follows that pattern. citeturn5search0

The current resource-management approach is also aligned with WebGL best practices. Browsers do not guarantee immediate GPU cleanup through JavaScript garbage collection, so materials, textures, buffers, and contexts must be managed explicitly. The application already disposes most of these resources and recreates textures when artwork changes. citeturn5search6turn6search10

### Where the present implementation is limited

The existing renderer is a good **preview renderer**, but it is not yet a complete **presentation renderer**.

The most significant gaps are:

| Gap | Current behavior | Consequence |
|---|---|---|
| Transparent rendering | Renderer is created with `alpha: false` and the scene always uses a background | Transparent PNG cannot be produced directly |
| Still-image export | No dedicated offscreen 3D export service is visible | Screenshot quality depends on viewport size |
| Carton thickness | Panels are effectively flat surfaces | Folded result can look like textured paper planes |
| Edge treatment | No visible bevel or rounded crease treatment | Silhouette appears computer-generated |
| Quality scaling | One interactive pixel ratio and one shadow configuration | No low/medium/high device adaptation |
| Post-processing | No AO, SMAA, TAA, depth of field, or final `OutputPass` pipeline | Limited depth, contact shading, and anti-aliasing |
| Camera UX | Projection switching exists, but product-style camera presets are limited | Users must manually find attractive views |
| Lighting UX | Lighting is hard-coded per scene preset | No direct-light position, softness, exposure, or shadow controls |
| Texture mode separation | One texture policy is used for interactive preview | High-resolution output cannot independently request more texture detail |
| Material semantics | “Photorealistic” uses one general physical material | Matte board, gloss varnish, lamination, foil, and unprinted board cannot be represented distinctly |

The current “photorealistic” material enables a small amount of clearcoat for all artwork. Clearcoat is intended for a distinct reflective coating layer and incurs additional per-pixel cost. It is more appropriate as a user-selectable varnish or lamination property than as a universal carton setting. Three.js also recommends an environment map when using `MeshPhysicalMaterial`, which the current photorealistic preset correctly supplies. citeturn4search0turn4search15

The current shadow camera is expanded according to a ground extent derived from the largest object dimension. Since directional-light shadow quality is distributed across the shadow camera’s covered area, an unnecessarily large frustum reduces effective shadow resolution. Three.js recommends keeping the shadow camera region and shadow texture as small as possible while still covering the subject. fileciteturn10file0 citeturn1search0

## Target rendering architecture

The renderer should be reorganized into a small set of explicit services while retaining the existing `BoxScene`, panel graph, and texture composer.

```text
Canonical project state
        │
        ├── BoxNetModel in millimeters
        ├── Artwork placement in millimeters
        ├── Panel roles and hinge graph
        └── Rendering preferences
                │
                ▼
        RenderSceneModel
        ├── Panel meshes and UVs
        ├── Thickness and edge geometry
        ├── Material assignments
        ├── Camera rig
        ├── Light rig
        └── Ground/background configuration
                │
       ┌────────┴─────────┐
       ▼                  ▼
RealtimeRenderer      StillRenderService
WebGL raster          Offscreen fixed-size render
Interactive preview   PNG/JPEG/WebP export
       │                  │
       └────────┬─────────┘
                ▼
        Shared preset system
```

### Rendering modes

The product should expose three user-facing modes, while internally reusing the same geometry and artwork mapping.

| Mode | Purpose | Rendering behavior |
|---|---|---|
| Technical | Artwork orientation, panel selection, folding inspection | Unlit or minimally lit, no tone mapping, no AO, optional outlines |
| Studio | Daily visual preview | PBR material, environment light, one cast shadow, fast anti-aliasing |
| Presentation | Final mockup export | High-resolution render target, stronger anti-aliasing, AO, optional depth of field and transparent background |

Technical mode should remain deliberately neutral. It should not change artwork appearance through dramatic lighting or tone mapping. This mode is an artwork-orientation and geometry inspection tool, not a beauty render.

Studio and Presentation modes should use a physically based linear workflow. Three.js performs lighting calculations in Linear-sRGB, while PNG and JPEG artwork textures normally represent sRGB color data and must be marked accordingly. Display output should then be converted back to sRGB. When post-processing is used, `OutputPass` should generally be the final color-conversion and tone-mapping stage. citeturn0search1turn0search10

A critical product disclaimer should be added:

> The 3D renderer is an sRGB visualization and presentation tool. It is not a color-managed CMYK or spot-color print proof.

Browser graphics workflows are primarily built around sRGB, whereas pharmaceutical packaging may contain CMYK process colors, Pantone or other spot colors, varnish, foil, embossing, and substrate-dependent appearance. The visual renderer can approximate those effects, but final color approval must remain in a controlled artwork or proofing workflow. citeturn0search1

### Quality states

The renderer should automatically transition between three internal quality states.

| State | Trigger | Proposed configuration |
|---|---|---|
| Interactive | Camera moving, fold slider active, control being dragged | Reduced resolution, no GTAO, no depth of field, basic shadow, SMAA or native MSAA |
| Settled | Camera and controls unchanged for approximately 200–400 ms | Full preview resolution, improved shadow, GTAO, optional TAA accumulation |
| Export | User requests an image | Fixed output resolution, full-quality texture, complete post-processing, offscreen rendering |

This approach reproduces the useful part of progressive rendering without immediately adopting a path tracer. Three.js `TAARenderPass` accumulates jittered samples across frames when the scene is stationary, producing higher-quality anti-aliasing. This is particularly well suited to CartonBuilder because the scene is normally static after the user stops rotating the box. citeturn3search8

During movement, SMAA is a suitable raster anti-aliasing option. The official pass operates in Linear-sRGB and must be ordered correctly relative to output color conversion. citeturn3search0turn0search10

### Backend strategy

`WebGLRenderer` should remain the production backend for the next major release. Modern Three.js `WebGLRenderer` uses WebGL 2, and the current CartonBuilder implementation is already built and tested around it. citeturn5search8

Three.js now positions `WebGPURenderer` as its next-generation renderer and provides an automatic WebGL 2 fallback. However, MDN still classifies WebGPU as limited availability rather than a broadly available baseline feature. Therefore, a direct WebGPU migration would introduce unnecessary compatibility and testing risk before the presentation feature set is mature. citeturn0search0turn0search3turn4search2

The architecture should nevertheless avoid hard-coding all logic directly into `BoxScene`. A small renderer interface will make a later WebGPU prototype possible:

```ts
interface CartonRenderer {
  initialize(sceneModel: RenderSceneModel): Promise<void>;
  resize(width: number, height: number, pixelRatio: number): void;
  render(reason: RenderReason): void;
  updateCamera(camera: CameraState): void;
  updateScenePreset(preset: ScenePreset): void;
  replaceArtwork(texture: CanvasImageSource): Promise<void>;
  exportImage(options: RenderExportOptions): Promise<Blob>;
  getDiagnostics(): RenderDiagnostics;
  dispose(): void;
}
```

The first implementation would be `WebGLCartonRenderer`. A future `WebGPUCartonRenderer` could be added behind a feature flag without changing carton or artwork state.

## Visual fidelity best practices

### Carton geometry

The single largest visual improvement will come from geometry rather than more lights.

A folded carton should no longer be represented only by infinitely thin planes. Each structural panel should eventually expose:

- exterior printed surface;
- interior board surface;
- narrow edge surface;
- configurable board thickness;
- small visual bevel or crease radius;
- hinge offset accounting for board thickness.

The first implementation should be **visual thickness**, not full physical folding simulation. Each panel can be constructed as a thin rectangular solid whose artwork UVs remain on the exterior face. The inner face can use a neutral board material, while the edge faces use a slightly darker paperboard tone.

The hinge pivot must then be shifted by approximately half the board thickness so adjacent solids meet more naturally. Mechanical collision handling between flaps should remain outside the first rendering milestone.

A practical model extension would be:

```ts
interface BoardAppearance {
  thicknessMm: number;
  interiorColor: string;
  edgeColor: string;
  finish: 'uncoated' | 'matte' | 'gloss' | 'custom';
  roughness: number;
  clearcoat: number;
  clearcoatRoughness: number;
}
```

Thickness must remain a model-space millimeter value, consistent with the application’s existing principle of storing structural measurements in millimeters. fileciteturn0file0 fileciteturn0file1

### Material profiles

CartonBuilder should provide semantic material profiles instead of exposing raw Three.js properties first.

| Profile | Recommended rendering model | Initial behavior |
|---|---|---|
| Uncoated board | `MeshStandardMaterial` | High roughness, low specular appearance |
| Matte coated | `MeshStandardMaterial` or lightweight physical material | Moderate-high roughness |
| Gloss laminated | `MeshPhysicalMaterial` | Lower base roughness with clearcoat |
| Spot varnish | Physical material plus mask map | Clearcoat only in masked artwork regions |
| Metallic foil | Separate masked material region | Metallic response only in defined areas |
| Technical | `MeshBasicMaterial` | Lighting-independent artwork display |

`MeshPhysicalMaterial` should be reserved for finishes that genuinely need its advanced layers. Three.js notes that the physical material has a higher per-pixel cost and that enabled features add further expense. citeturn4search0

The first release should include Uncoated, Matte, and Gloss profiles. Spot varnish and metallic foil should be introduced only after the artwork model can carry effect masks independently from the printed color texture.

### Lighting

A strong studio result does not require many shadow-casting lights. The recommended real-time light rig is:

```text
PMREM environment
        +
One directional key light with shadow
        +
Optional non-shadow fill or hemisphere contribution
        +
Shadow-receiving floor
```

Shadow maps require the scene to be rendered from the perspective of every shadow-casting light. Multiple shadow lights multiply rendering work, and point-light shadows are particularly expensive because the scene is rendered in six directions. One shadow-casting directional light is therefore the appropriate default. citeturn1search0

The existing `RoomEnvironment` and PMREM setup should be retained. PMREM prefilters an environment map so materials can efficiently sample different blur levels according to roughness, matching Three.js’ PBR lighting model. citeturn4search1turn4search15

User-facing light controls should be presented in product language:

| UI control | Internal property |
|---|---|
| Horizontal | Key-light azimuth |
| Vertical | Key-light elevation |
| Brightness | Key-light intensity |
| Softness | Shadow radius, filter, or light-size approximation |
| Ambient | Environment intensity |
| Shadow strength | Ground `ShadowMaterial.opacity` |
| Exposure | Renderer tone-mapping exposure |

The light target should remain centered on the carton bounding sphere. The directional-light shadow camera should be fitted tightly around the visible folded box, with limited padding. The shadow camera should be recalculated after folding, box-dimension changes, and major camera-preset changes.

### Ambient occlusion and contact depth

The current floor shadow gives useful grounding but does not darken small creases or panel intersections. GTAO can provide contact depth around folds, bottom edges, and overlapping surfaces. Three.js documents that `GTAOPass` produces better quality than `SSAOPass`, at higher cost. citeturn3search3

The recommended policy is:

| Quality state | AO behavior |
|---|---|
| Interactive | Disabled |
| Settled preview | GTAO at half or reduced resolution |
| Export | GTAO at full or high resolution |
| Technical mode | Disabled |

AO strength must remain subtle. Excessive AO can make white pharmaceutical cartons look dirty and can falsely alter artwork contrast.

### Camera behavior

CartonBuilder should add deterministic camera presets:

| Preset | Purpose |
|---|---|
| Front | Artwork inspection |
| Front-right | Standard product mockup |
| Front-left | Alternative product mockup |
| Top-front | Shows top closure and front panel |
| Isometric | Technical spatial understanding |
| Selected panel | Focuses the currently selected panel |
| Custom | User-controlled orbit view |

The application should store camera direction, target, projection, field of view, and framing margin in a serializable `CameraState`. Camera presets should be based on the carton bounding sphere rather than fixed world coordinates, so they behave consistently across a small pharmaceutical carton and a much larger box.

Perspective control should be presented as a simple slider but implemented through a bounded field-of-view range while maintaining framing. Orthographic mode should remain available for technical inspection.

Depth of field should be restricted to Presentation mode and disabled by default. Three.js provides `BokehPass` with focus, aperture, and maximum-blur controls, but blur can make mandatory text and artwork elements harder to inspect. citeturn3search5

### Artwork texture quality

The current single-texture workflow is correct. Artwork should continue to be composited in flat-net space and sampled by panel UVs derived from that same flat geometry. This guarantees continuity across folds and avoids the duplicated Front/Side/Top artwork model used by simplified mockup tools. fileciteturn0file0 fileciteturn0file1

The current texture policy already caps the result at 4096 pixels and sixteen million total pixels. That is a good interactive safety limit, but preview and export textures should be separated. fileciteturn11file0

| Texture type | Proposed policy |
|---|---|
| Interaction texture | 1024–2048 maximum edge where possible |
| Standard preview texture | Up to 4096 edge and existing pixel cap |
| Export texture | Calculated from output resolution and visible texel density |
| Path-traced texture | Same as export texture or a dedicated high-quality version |

Anisotropic filtering should remain enabled because it improves texture clarity at steep viewing angles, although it increases texture sampling cost. citeturn6search10

The current two-pixel panel bleed should become configurable or calculated from texture scale. Automated seam fixtures should test white, black, high-contrast, and one-pixel border artwork at extreme camera angles and multiple mip levels.

## Performance, export, and compatibility

### Adaptive performance

The current hard cap of `Math.min(devicePixelRatio, 2)` is a reasonable first safety measure, but an export and post-processing pipeline benefits from explicitly managing drawing-buffer dimensions. Three.js guidance explains that high-density displays may require many times more fragment work and recommends controlling the actual drawing-buffer size rather than blindly rendering at full device pixel ratio. citeturn5search1

A `QualityManager` should select one of three profiles:

| Profile | Preview scale | Shadow map | AO | Settled TAA | Texture cap |
|---|---:|---:|---|---|---:|
| Low | 0.75–1.0 | 512 | Off | Off | 2048 |
| Medium | 1.0–1.25 | 1024 | Half resolution | Optional | 4096 |
| High | 1.25–1.5 | 2048 | High resolution | On | 4096–8192, device permitting |

The profile should be based on measured frame time rather than GPU model strings. After a short warm-up render, the renderer can reduce or increase preview scale to meet its frame budget.

Proposed performance targets for the reference six-panel carton are:

| Metric | Desktop target | Lower-power target |
|---|---:|---:|
| Camera interaction | At least 55 FPS | At least 30 FPS |
| Fold-slider interaction | At least 55 FPS | At least 30 FPS |
| 3D initialization after lazy load | Under 1.5 seconds | Under 3 seconds |
| 2048-pixel export | Under 3 seconds | Under 8 seconds |
| 4096-pixel raster export | Under 8 seconds | Under 20 seconds |

These are project targets rather than browser guarantees and should be calibrated against an agreed device matrix.

### High-resolution render export

The 3D image should not be exported by simply saving the visible canvas. Instead, introduce a `StillRenderService` that:

1. creates a fixed-size `WebGLRenderTarget`;
2. temporarily applies export-quality settings;
3. frames the camera for the requested aspect ratio;
4. renders into the target;
5. reads pixels asynchronously;
6. vertically flips the pixel rows;
7. transfers the result into an `OffscreenCanvas` or HTML canvas;
8. encodes the image through `toBlob()`;
9. restores interactive renderer state;
10. disposes the target.

Three.js supports rendering to a `WebGLRenderTarget` and provides an asynchronous, non-blocking `readRenderTargetPixelsAsync()` method, which is preferable to synchronous readback when available. citeturn6search1turn6search4

The export UI should offer:

| Format | Options |
|---|---|
| PNG | Transparent, white, studio, or custom background |
| JPEG | White, studio, or custom background; quality control |
| WebP | Background and quality control |
| Resolution | 1024, 2048, 4096, custom |
| Aspect ratio | Square, original viewport, landscape, portrait |
| Camera | Current view or named preset |
| Quality | Standard or High |

`HTMLCanvasElement.toBlob()` is widely supported, guarantees PNG support, commonly supports JPEG and WebP, and avoids the large in-memory strings created by `toDataURL()`. Canvas-exported files may contain 96-DPI metadata, so the UI should describe 3D output primarily in pixel dimensions rather than presenting it as a print-resolution file. citeturn6search2turn6search14

### Transparent background

Transparent output should be implemented through the offscreen export path, independently from the interactive scene.

For transparent export:

```text
Render target alpha enabled
Scene background = null
Ground hidden
Clear alpha = 0
PNG or WebP selected
```

The normal interactive renderer may continue using an opaque background if changing its context attributes introduces regression risk. The export renderer can be a short-lived renderer or an alpha-capable shared renderer whose visible background is implemented with scene geometry or clear color.

### Very large exports

Before creating a render target, the application should check `renderer.capabilities.maxTextureSize` and `maxSamples`. Three.js exposes these GPU-dependent limits. citeturn6search1

If a requested render exceeds available dimensions, CartonBuilder should either reduce the resolution with a clear warning or use tiled export. Tiled export renders multiple camera subregions and assembles them in a 2D canvas. This will also be useful for any future path-tracing mode.

### Resource stability

Replacing artwork currently disposes the previous GPU texture, which is correct. The export service must similarly dispose all render targets, temporary textures, post-processing passes, and canvases once the resulting Blob has been produced. fileciteturn10file0 citeturn5search6turn6search10

The existing context-loss handling should be retained and added to automated tests. When a WebGL context is restored, textures and buffers created before the loss are invalid and must be recreated. citeturn5search5turn5search7

### Progressive path tracing

A path tracer can eventually provide soft area-light shadows, more realistic global illumination, improved reflections, and genuine depth of field. The most relevant Three.js ecosystem candidate is `three-gpu-pathtracer`, which uses WebGL 2 and `three-mesh-bvh`, supports PBR materials, textures, environment maps, tiled rendering, depth of field, and low-resolution dynamic previews. fileciteturn13file0

It should not become the primary interactive renderer because:

- folding or camera movement invalidates accumulated samples;
- artwork replacement requires rebuilding or resynchronizing path-tracer resources;
- progressive convergence introduces latency;
- it is an external library rather than Three.js core;
- device performance will vary significantly;
- raster rendering is already sufficient for technical inspection.

The recommended future workflow is:

```text
User moves camera
        ↓
Realtime raster preview
        ↓
Camera stops
        ↓
Optional “High quality render” requested
        ↓
Path tracer starts at low resolution
        ↓
Samples progressively accumulate
        ↓
User downloads when quality is sufficient
```

A prototype should compare raster High mode and path tracing on the same test scenes before any production commitment. If the path tracer does not deliver a clearly visible improvement for simple paperboard cartons, TAA plus GTAO plus improved geometry will be the better product investment.

## Implementation roadmap

The roadmap below is based on the existing repository rather than a greenfield implementation. It assumes one developer and normal code-review and testing time.

| Phase | Duration | Main deliverables | Exit condition |
|---|---:|---|---|
| Rendering foundation | 1–2 weeks | Render settings model, quality profiles, diagnostics, baseline screenshots | Existing 3D behavior preserved and benchmarked |
| Presentation MVP | 2–3 weeks | Camera presets, background modes, transparent PNG, 2K/4K offscreen export | Users can generate a clean product image |
| Lighting and material system | 2–3 weeks | Light rig controls, board finish presets, exposure, improved shadow framing | Studio renders are repeatable and configurable |
| Geometry fidelity | 2–3 weeks | Board thickness, inner and edge surfaces, hinge offset, visual bevels | Carton silhouette and folds no longer look paper-thin |
| Settled-camera quality | 2–3 weeks | SMAA, GTAO, TAA accumulation, final output pass | Stationary image visibly improves without blocking interaction |
| Performance hardening | 1–2 weeks | Adaptive quality, memory tests, context-loss tests, device matrix | Stable on agreed desktop and mobile devices |
| Path-tracing evaluation | 1–2 weeks | Experimental branch and side-by-side comparison | Go/no-go decision supported by evidence |
| Optional path-traced render | 4–8 weeks | Progressive still renderer, tiled output, quality and sample controls | Production-ready only if prototype passes quality and performance gates |

### Rendering foundation

The first phase should not change the appearance substantially. Its purpose is to reduce future integration risk.

Implement:

- `RenderSettings` stored separately from structural carton state;
- `CameraState`;
- `LightRigState`;
- `MaterialProfile`;
- `RenderQualityProfile`;
- `RenderDiagnostics`;
- an event-based render scheduler;
- baseline screenshot fixtures for existing presets.

The existing lazy-loading facade should remain. The new export service and post-processing code should also load only when the user enters 3D preview or requests an image. fileciteturn7file0

Recommended initial settings model:

```ts
interface RenderSettings {
  mode: 'technical' | 'studio' | 'presentation';
  quality: 'auto' | 'low' | 'medium' | 'high';
  background: {
    type: 'transparent' | 'solid' | 'studio';
    color: string;
  };
  camera: CameraState;
  lighting: {
    azimuthDeg: number;
    elevationDeg: number;
    keyIntensity: number;
    ambientIntensity: number;
    shadowStrength: number;
    shadowSoftness: number;
    exposure: number;
  };
  material: {
    profile: 'uncoated' | 'matte' | 'gloss';
    thicknessMm: number;
  };
  effects: {
    ambientOcclusion: boolean;
    depthOfField: boolean;
    progressiveAA: boolean;
  };
}
```

### Presentation MVP

This is the first user-visible delivery and should be prioritized before geometry or path tracing.

Deliver:

- transparent background;
- white background;
- studio background;
- current-view export;
- square 2048 × 2048 PNG;
- 4096 × 4096 PNG;
- JPEG export;
- deterministic front, front-right, front-left, top-front, and isometric cameras;
- Fit Object;
- Reset View;
- separate “Download 3D Render” action.

The UI should separate technical and presentation outputs:

```text
Technical export
PDF 1:1
Dieline SVG
Artwork proof PNG

Presentation export
3D PNG
Transparent PNG
3D JPEG
```

### Lighting and material system

Replace hard-coded preset values with serializable scene presets.

Initial presets:

| Preset | Background | Material | Lighting | Shadow |
|---|---|---|---|---|
| Technical | Neutral light grey | Unlit | None | None |
| Clean Studio | White/light grey | Matte | Soft front-right | Light |
| Product Catalogue | White | Matte or gloss | Even high-key | Moderate |
| Soft Shadow | Warm neutral | Matte | Large soft key | Soft |
| Dramatic | Dark neutral | Gloss optional | Side key | Strong |
| Transparent | None | Selected finish | Studio key | None |

The preset should apply defaults but still allow manual refinement.

### Geometry fidelity

Implement panel thickness in two steps.

**Visual thickness** should add exterior, interior, and edge faces without attempting collisions.

**Corrected folding thickness** should offset hinge pivots and adjust panel placement so adjacent board solids align more naturally.

The default thickness may be initialized from a product setting, but it should not be presented as structurally validated unless CartonBuilder later supports board-caliper and crease-compensation rules.

### Settled-camera quality

Create a post-processing pipeline:

```text
RenderPass
    ↓
GTAO
    ↓
SMAA for interactive mode
or TAA accumulation for settled/export mode
    ↓
Optional BokehPass
    ↓
OutputPass
```

Not all effects should run simultaneously during interaction. GTAO and TAA should activate only after the camera has settled.

The implementation must ensure that output color conversion is performed once. Incorrect or duplicated sRGB conversion can make the scene globally too dark, too light, or change shading behavior. citeturn0search1turn0search10

### Path-tracing decision gate

The prototype must render the same reference carton with:

- current photorealistic raster preset;
- improved raster High preset;
- path tracer after a fixed number of samples;
- path tracer after a fixed time budget.

The path tracer should proceed to production only when it satisfies all of the following:

| Criterion | Required result |
|---|---|
| Quality | Clear improvement in soft shadow, reflection, or depth realism |
| Text readability | Fine carton text remains sharp and stable |
| Time | Useful preview appears within an acceptable wait |
| Compatibility | Works on the agreed browser and device matrix |
| Memory | Does not exceed defined GPU and system memory budgets |
| Export | Supports target resolution or tiled rendering reliably |
| Maintenance | Three.js upgrades can be managed without excessive custom patches |

## Definition of done and risk controls

### Functional acceptance

The rendering programme should be considered complete when a user can:

1. switch between Technical, Studio, and Presentation rendering;
2. select a deterministic camera preset;
3. orbit and zoom smoothly;
4. adjust perspective, light direction, ambient level, exposure, and shadow;
5. select matte, gloss, or uncoated board appearance;
6. see realistic board thickness and interior surfaces;
7. export a transparent PNG;
8. export 2048- and 4096-pixel studio images;
9. reproduce the same render from saved project settings;
10. return to technical preview without any artwork or geometry change.

### Visual acceptance

The test fixture library should include:

| Fixture | Purpose |
|---|---|
| White carton with black fine text | Detect blur, tone, and AO contamination |
| Black carton with white text | Detect shadow clipping and color conversion errors |
| Artwork crossing two folds | Verify UV continuity |
| One-pixel panel-border artwork | Detect texture seams |
| High-saturation RGB artwork | Detect color-space errors |
| Front/back orientation chart | Detect flipped or rotated panels |
| Matte and gloss variants | Validate material differences |
| Open, half-folded, and closed states | Validate hinges and thickness |
| Transparent export over checkerboard | Validate alpha edges |
| Very wide and very tall cartons | Validate camera fitting and shadow frustum |

### Proposed quality targets

| Requirement | Target |
|---|---|
| UV continuity | No visible seam at normal viewing distance |
| Artwork orientation | Exact agreement between 2D panel mapping and 3D panel |
| Texture replacement | No retained previous-artwork GPU resource |
| Memory stability | No sustained increase after twenty replacement/export cycles |
| Alpha export | Clean edges without opaque background halo |
| Camera presets | Same composition for the same carton dimensions and aspect ratio |
| Render reproducibility | Same settings produce visually equivalent output |
| Context recovery | Renderer rebuilds after simulated context loss |
| Technical mode | Artwork unaffected by presentation tone mapping or AO |
| Accessibility | Every canvas operation has an equivalent DOM control or textual status |

### Primary risks

| Risk | Impact | Mitigation |
|---|---|---|
| Presentation renderer mistaken for print proof | Regulatory or approval misunderstanding | Explicit sRGB visualization disclaimer; retain technical proof workflow |
| Excessive AO or tone mapping alters artwork | Misleading visual appearance | Technical mode bypass; restrained presets; regression fixtures |
| High-DPI rendering overloads mobile GPUs | Low frame rate or context loss | Adaptive resolution and measured quality profiles |
| Large artwork exhausts GPU memory | Crash or context loss | Separate preview/export textures; device capability checks |
| Thickness breaks fold alignment | Gaps or panel intersections | Two-stage thickness rollout and fold fixtures |
| Post-processing double-converts color | Incorrect brightness or saturation | Single final output pass and pixel-reference tests |
| Path tracer increases complexity without visible benefit | Delayed roadmap | Mandatory prototype and go/no-go gate |
| WebGPU incompatibility | Browser-specific failures | Retain WebGL production backend and feature-flag prototypes |
| Repeated exports leak render targets | Progressive instability | Explicit disposal and memory stress tests |
| Transparent export creates edge artifacts | Poor presentation files | Premultiplied-alpha tests on light and dark backgrounds |

The most valuable near-term product increment is therefore not “path tracing.” It is a dedicated **Presentation Render MVP** built on the current WebGL renderer: transparent PNG, deterministic camera presets, user-controllable studio lighting, tightly fitted shadows, high-resolution offscreen export, and distinct board finishes.

After that foundation, geometry thickness, restrained GTAO, SMAA during interaction, and TAA after the camera settles should bring CartonBuilder close to the visual quality expected from commercial browser mockup tools while preserving its much stronger technical model. Full path tracing should remain an optional high-quality still-render layer, never a replacement for the fast technical preview.
