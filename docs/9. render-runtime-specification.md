# CartonBuilder Presentation Render Runtime

This document describes the implemented fourth workflow step, **Render**. It
complements the technical Preview specification: Preview is for inspecting the
fold graph and dieline; Render is for producing a reproducible closed-carton
presentation image.

## Workflow and state ownership

Render is enabled only when the BoxNet model is complete and at least one visible
artwork entry is available. Preview is suspended while Render is active. The two
surfaces own separate Three.js scenes, so orbit, fold progress, selections, and
GPU resources are not shared mutable state.

Render always constructs its scene with `foldProgress = 1`. Returning to Preview
does not alter its technical fold, camera, or scene preset.

The canonical sources remain `BoxNetModel` and `ArtworkModel[]`. Render derives a
`RenderSceneModel` and uses the same flat-net artwork composition as Preview:
visible entries only, original layer order, crop, rotation, opacity, PDF-layer
visibility, and panel UV continuity are preserved. Render never writes back to
artwork or box geometry.

## Persisted settings

`src/render/RenderSettings.js` defines the defaults and sanitizes every value
before it reaches the renderer or project snapshot. Unknown enums fall back to
defaults, numbers are clamped, vectors must contain finite values, colors must be
six-digit hex values, and the long edge is limited to 2048 or 4096 pixels.

Schema version 4 adds the following project field:

```js
{
  render: {
    presetId, aspect, longEdge, camera, background, lighting,
    shadows, material, quality, effects
  }
}
```

The v2 → v4 migrations inject sanitized defaults and do not change artwork,
box, history, or existing view state. Board appearance is session-only unless
saved in a named Render preset. Transient renderer information, GPU handles,
export progress, and diagnostics are never serialized. Named presets are
presentation presets; the project stores the currently applied basic/effects
settings.

The current project schema is version 5. Its additional migration only rebases
legacy cropped artwork geometry and corresponding history states; the Render
settings contract introduced by version 4 is unchanged.

## Renderer contract

`WebGLCartonRenderer` is the presentation adapter behind the Render controller.
It uses the existing procedural panel geometry and fold graph, but creates its
own `WebGLRenderer` with alpha support, sRGB output, a PBR board material, one
directional shadow light, a RoomEnvironment PMREM, and a ground/contact shadow
receiver. Uncoated and Matte use `MeshStandardMaterial`; Gloss uses
`MeshPhysicalMaterial`.

The Preview scene remains intentionally flat and technical. Render uses solid
presentation panels with thickness/bevel, interior/edge material groups, and
the independent quality states `interactive → settled → export`. Interactive
uses SMAA/native raster; settled/export can enable GTAO, TAA, and explicit DOF.
`OutputPass` is the final color-conversion pass. WebGPU is not used, and path
tracing is a disabled-by-default gated experiment.

## Still export

`StillRenderService` calculates the exact frame dimensions:

| Aspect | 2048 | 4096 |
| --- | --- | --- |
| 1:1 | 2048×2048 | 4096×4096 |
| 4:3 | 2048×1536 | 4096×3072 |
| 16:9 | 2048×1152 | 4096×2304 |
| 3:4 | 1536×2048 | 3072×4096 |

The service renders to a temporary `WebGLRenderTarget`, reads pixels
asynchronously when supported, flips WebGL rows, and encodes through
`OffscreenCanvas` or a temporary DOM canvas. It does not set
`preserveDrawingBuffer: true`. JPEG is encoded at quality 0.94 and is always
composited on an opaque background. PNG supports transparent object-only output
or a transparent shadow catcher. Render targets and temporary resources are
disposed in `finally` blocks.

Each export accepts an `AbortSignal`. Starting a new export, replacing artwork,
changing Render settings, resetting the project, or losing the graphics context
cancels stale work. A stale promise cannot publish an old download.

Output names use the box dimensions and applied preset:

```text
carton-render-{width}x{height}x{depth}mm-{presetId}-{longEdge}.png
carton-render-{width}x{height}x{depth}mm-{presetId}-{longEdge}.jpg
```

Before allocation the service compares the target against reported texture and
renderbuffer limits. If the device cannot allocate 4096, the UI reports a clear
GPU-limit error and the user can select 2048.

## Color and production boundaries

Artwork textures are treated as sRGB and material/data maps as non-color data.
The Render surface is an sRGB presentation visualization; it is not CMYK,
ICC/Pantone, overprint, trapping, varnish, foil, embossing, or print-proof
validation. Technical SVG/PDF output remains the production-oriented dieline
workflow.

## Test coverage

Unit coverage validates settings/effects sanitization and frame dimensions,
deterministic presets, board appearance and solid geometry, postprocessing pass
plans, quality state transitions, closed Render scene construction without
canonical-state mutation, offscreen PNG/JPG options, GPU limits, abort handling,
and v2 → v4 migration.
Browser coverage validates the disabled stepper state, Preview → Render
navigation, closed-scene isolation, settings persistence in the active session,
and a real 2048×1536 PNG export.

## Deferred milestones

Collision simulation, production valve mechanics, CMYK/ICC/Pantone proofing,
WebGPU, and production path tracing remain deferred. The path-tracing adapter
is only loaded when `VITE_ENABLE_RENDER_PATH_TRACING=true` and an explicitly
compatible optional dependency is installed.
