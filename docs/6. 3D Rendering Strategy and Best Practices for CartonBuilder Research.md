# 3D Rendering Strategy and Best Practices for CartonBuilder

## Executive assessment

CartonBuilder should not treat photorealistic rendering as a replacement for its existing technical 3D preview. The strongest product architecture is a **dual-mode rendering system**:

| Mode | Primary purpose | Rendering priority |
|---|---|---|
| **Technical 3D** | Verify folding, panel orientation, artwork continuity, dimensions, flap relationships, and dieline correctness | Accuracy, responsiveness, clarity |
| **Presentation 3D** | Produce client-facing mockups, transparent PNGs, catalogue images, and presentation visuals | Realism, lighting, materials, shadows, image quality |

This division is consistent with the project’s earlier research: the millimeter-native 2D model should remain authoritative, panel UV coordinates should be derived from the flat net, and folding should modify panel transforms without changing artwork mapping. The architecture diagram on page 2 of the supplied PDF separates structural, artwork, history, and view state; the implementation diagram on page 16 similarly places the dependable 2D model before the 3D layer. fileciteturn0file0 fileciteturn0file1

The currently published CartonBuilder already exposes box dimensions, panel construction, artwork positioning in millimeters, effective DPI, layers, history, folding controls, camera/style selection, and PNG, JPG, SVG, and PDF export. That means the next rendering work should improve the existing derived 3D view rather than introduce an independent model or a separate front/side/top artwork workflow. citeturn1view0

Appsforlife’s free editor demonstrates the value of a presentation-oriented mode. It exposes camera distance, perspective, depth of field, focus, direct-light position and blur, object lighting, floor shadow, transparent background, and image download. It restarts accumulation after camera or parameter changes and advises allowing roughly 10–15 seconds for noise to settle. This behavior is consistent with progressive rendering, although the public page does not identify the exact rendering engine. citeturn1view2

Appsforlife also documents the limitations of its free workflow: front artwork is duplicated on the back, side artwork is duplicated on the opposite side, uploaded images are recommended to remain at or below 2048 pixels, and professional dieline-based work is handled by more specialized products. Those simplifications are suitable for a mockup generator but should **not** be adopted by CartonBuilder, whose competitive advantage is a real dieline, one coherent artwork coordinate system, and technically meaningful folding. citeturn1view2turn0search1turn0search2

The recommended direction is therefore:

> **Keep one authoritative carton model, but provide two visual interpretations of it: an immediate technical renderer and an optional high-quality presentation renderer.**

### Strategic technology decision

| Option | Recommendation for CartonBuilder | Reason |
|---|---|---|
| Three.js `WebGLRenderer` | **Production default now** | Mature WebGL 2 renderer, compatible with the traditional Three.js post-processing stack and community path-tracing options |
| Three.js `WebGPURenderer` | **Architecture-ready pilot** | Future-facing renderer with WebGPU, WebGL 2 fallback, TSL, node materials, and modern render pipelines |
| Enhanced raster rendering | **Main presentation implementation** | Delivers most visible quality improvements without path-tracing latency |
| Progressive path tracing | **Optional high-quality still mode** | Appropriate for downloadable hero renders, not continuous editing |
| Server-side rendering | **Not needed initially** | The carton scene is simple enough for local rendering and local processing preserves artwork privacy |

`WebGLRenderer` now targets WebGL 2; Three.js no longer supports WebGL 1 through that renderer. `WebGPURenderer` attempts WebGPU first and falls back to WebGL 2, but WebGPU remains classified by MDN as not universally available, and migration has practical constraints: legacy `ShaderMaterial`, `RawShaderMaterial`, and `onBeforeCompile()` customization are not supported by `WebGPURenderer`. citeturn2search3turn5search0turn5search1turn5search4

For that reason, an immediate wholesale migration to WebGPU would add risk without materially improving a six-to-twelve-panel carton scene. The correct engineering move is to hide renderer-specific behavior behind an adapter, continue shipping the stable WebGL renderer, and test a TSL/WebGPU branch separately.

## Rendering architecture and source of truth

The 3D scene must remain a disposable projection of canonical project state. No important geometry, artwork placement, material assignment, fold relationship, or camera preset should exist only inside Three.js objects.

A robust architecture is:

```text
Canonical project state in millimeters
        │
        ├── 2D SVG editor
        ├── PDF/SVG technical export
        ├── Technical 3D scene adapter
        └── Presentation 3D scene adapter
                ├── realtime raster pipeline
                └── optional progressive still renderer
```

This preserves the central finding from the supplied research: panel UVs should be generated from flat-net coordinates, not produced by unwrapping a finished folded mesh. Three.js `BufferGeometry` supports explicit position, normal, index, UV, and custom attributes, making it appropriate for a procedural panel pipeline. fileciteturn0file0 citeturn13search11

### Canonical rendering model

The project model should be expanded to include rendering properties without making the renderer authoritative:

```ts
interface CartonRenderModel {
  board: {
    thicknessMm: number;
    outsideMaterial: MaterialPreset;
    insideMaterial: MaterialPreset;
    edgeColor: string;
  };

  panels: Array<{
    id: string;
    role: string;
    flatPathMm: Path2DModel;
    hinge?: {
      parentPanelId: string;
      edgeId: string;
      closedAngleDeg: number;
    };
    artworkUvTransform: Matrix3Model;
    renderOrder?: number;
  }>;

  presentation: {
    presetId: string;
    background: BackgroundSettings;
    camera: CameraSettings;
    lighting: LightingSettings;
    shadow: ShadowSettings;
    quality: QualitySettings;
  };
}
```

The distinction between project state and GPU state is important. Three.js textures, geometries, render targets, materials, and environment maps are resources that may need to be recreated after artwork replacement, renderer reinitialization, or context restoration. They should be generated from serializable model state, not serialized as application truth. Three.js exposes renderer statistics for active geometries and textures, and its documentation requires explicit disposal of replaced texture and material resources. citeturn10search9turn2search15

### Renderer abstraction

A renderer-facing contract should prevent UI code from depending directly on WebGL- or WebGPU-specific features:

```ts
interface CartonRenderer {
  initialize(container: HTMLElement): Promise<void>;
  setProject(model: CartonRenderModel): Promise<void>;
  setFoldProgress(value: number): void;
  setCamera(settings: CameraSettings): void;
  setPresentation(settings: PresentationSettings): void;
  resize(widthCssPx: number, heightCssPx: number): void;
  renderInteractive(): void;
  exportStill(options: StillExportOptions): Promise<Blob>;
  dispose(): void;
}
```

Recommended implementations are:

```text
WebGLCartonRenderer
WebGPUCartonRendererExperimental
PathTracedStillRenderer
```

The path-traced renderer should consume a cloned or normalized version of the same scene description. It should not become responsible for editing, folding state, panel selection, or project serialization.

### Scene composition

The scene should be divided into clear layers:

| Scene group | Contents | Present in technical mode | Present in presentation mode |
|---|---|---:|---:|
| `cartonOuter` | Printed external surfaces | Yes | Yes |
| `cartonInner` | Internal board surfaces | Optional | Yes |
| `cartonEdges` | Exposed thickness and edge strips | Optional | Yes |
| `technicalOverlay` | Panel IDs, fold lines, selected-panel highlight | Yes | Optional |
| `studioFloor` | Shadow receiver or visible floor | No | Yes |
| `lightingRig` | Environment, key, fill, rim lights | Simplified | Yes |
| `helpers` | Axes, camera and shadow diagnostics | Development only | Development only |

This separation allows technical overlays to be disabled for export without altering carton geometry or materials. It also prevents dieline lines from being baked accidentally into customer-facing renders.

## Carton geometry and material realism

The largest visible realism improvement will not come from path tracing. It will come from replacing perfectly thin, razor-edged planes with a physically plausible carton representation.

### Panel thickness and visible edges

A single `PlaneGeometry` has no thickness, no exposed edge, and no independent inside surface. That creates several visual problems:

- silhouettes look unnaturally sharp;
- top and side edges disappear at some angles;
- open flaps have identical front and back appearance;
- contact shadows are too clean;
- overlapping closure flaps can produce depth conflicts.

For Presentation 3D, each panel should be rendered as a thin solid or as a lightweight composite containing an outside face, inside face, and narrow edge strips. The canonical board thickness should remain measured in millimeters. A typical implementation can still use only a few quads per panel, so it does not require complex modeling.

The outside face should sit at approximately `+thickness / 2`, the inside face at `-thickness / 2`, and perimeter strips should connect them. Hinge pivots should be calculated from the relevant board surface rather than from the panel centreline when high geometric fidelity is required. This avoids visible gaps or interpenetration around folds.

For the first presentation release, a simpler compromise is acceptable:

1. retain the current hinge-centre folding;
2. add front and back surfaces;
3. add visible edge strips;
4. apply a small geometric bevel only to external presentation edges;
5. refine thickness-aware hinge compensation later.

This sequence avoids turning carton kinematics into a blocker for immediate visual improvement.

### Edge bevels

Perfect mathematical edges create an artificial result because they do not catch a highlight. Even a very small chamfer generates a narrow lighting transition that communicates thickness and material.

The bevel should be relative to board thickness rather than box dimensions. A practical starting policy is:

```text
bevelRadius = clamp(boardThicknessMm × 0.15, 0.05 mm, 0.25 mm)
```

This is a visual preset, not a manufacturing assertion. The value should be reduced or disabled in Technical 3D, where exact panel boundaries matter more than presentation.

### Outside and inside materials

Avoid using one double-sided printed material for both surfaces. Real cartons usually have a distinct internal appearance, and artwork orientation on the back side of a double-sided material can be visually misleading.

Use separate material groups:

```text
Outside: uploaded artwork + selected print finish
Inside: unprinted board color or optional internal artwork
Edges: board fibre/edge color
```

`MeshStandardMaterial` uses the metallic-roughness PBR workflow and supports base-color, roughness, metalness, normal, bump, displacement, and ambient-occlusion maps. Three.js recommends an environment map for best results with PBR materials. citeturn6search0turn8search12

### Material presets for packaging

CartonBuilder should expose understandable packaging presets rather than raw shader terminology.

| User-facing preset | Suggested implementation | Notes |
|---|---|---|
| **Uncoated board** | `metalness: 0`, high roughness, very subtle fibre normal map | Soft broad highlights |
| **Coated carton** | `metalness: 0`, medium-high roughness, smoother normal map | Suitable general pharmaceutical carton default |
| **Gloss varnish** | Base material plus moderate clearcoat and low clearcoat roughness | Use selectively or over the full artwork |
| **Matte varnish** | High base roughness, low-strength broad clearcoat | Avoid making the result completely flat |
| **Spot UV** | Clearcoat intensity and roughness masks generated from a spot layer | Requires a finish mask input |
| **Metallic foil** | Metalness mask plus foil base color and lower roughness | Only foil regions should be metallic |
| **Emboss/deboss** | Normal or bump map for preview; optional displacement for close-up export | Normal mapping is cheaper and safer |
| **Holographic finish** | Optional iridescence implementation | Advanced presentation feature |

`MeshPhysicalMaterial` extends the standard PBR material with clearcoat, iridescence, advanced reflectivity, anisotropy, transmission, and other effects, but Three.js warns that enabled physical features add per-pixel cost and work best with an environment map. Khronos defines clearcoat as a protective layer over the base material and explicitly gives varnish as an example use. citeturn2search1turn6search2

The implementation should prefer `MeshStandardMaterial` for ordinary board and upgrade only affected surfaces to `MeshPhysicalMaterial`. A complete box does not need the more expensive physical shader merely because one small region contains spot varnish.

### Texture roles and color spaces

Artwork/base-color textures contain color and should be marked as sRGB. Roughness, metalness, normal, bump, clearcoat, mask, and ambient-occlusion textures are data maps and should remain in a non-color space. Three.js documents this distinction directly. citeturn6search0turn2search15

A correct texture assignment should resemble:

```ts
artworkTexture.colorSpace = THREE.SRGBColorSpace;

roughnessTexture.colorSpace = THREE.NoColorSpace;
normalTexture.colorSpace = THREE.NoColorSpace;
metalnessTexture.colorSpace = THREE.NoColorSpace;
finishMaskTexture.colorSpace = THREE.NoColorSpace;
```

Failure to distinguish color textures from data textures produces incorrect brightness, roughness, and normal-map response even when the rest of the lighting setup is correct.

### Artwork texture policy

The single full-net artwork texture remains the best default because it preserves continuity across fold boundaries and matches the authoritative 2D layout. UVs should still be computed from flat artwork coordinates, as specified in the supplied project research. fileciteturn0file1

However, texture resolution should be adaptive rather than fixed globally. Appsforlife asks users to keep uploaded artwork dimensions at or below 2048 pixels, but CartonBuilder should not adopt that limit as an unconditional production rule. The renderer can query `maxTextureSize` and maximum anisotropy from Three.js capabilities, then generate an appropriate preview texture for the detected device. citeturn1view2turn13search2

Recommended policy:

| Context | Texture strategy |
|---|---|
| Interactive mobile preview | Long edge approximately 1024–2048 px |
| Interactive desktop preview | Long edge approximately 2048–4096 px |
| High-quality still | Use the highest safe texture size required by the camera framing |
| Technical PDF/SVG export | Do not reuse the 3D preview texture as production artwork |
| Oversized artwork | Generate a downsampled 3D proxy while preserving the original for technical export |

This maintains responsiveness without reducing the quality of the canonical artwork asset.

Texture filtering should use mipmaps for zoomed-out views and device-supported anisotropy for oblique side panels. Three.js notes that anisotropy reduces blur along the direction of highest texel density at the cost of additional texture sampling. citeturn2search15turn13search2

### Fold seams, overlap, and z-fighting

Closed carton structures contain flap overlaps that cannot all occupy the same mathematical surface. The renderer should assign physical offsets based on board thickness and assembly order:

```text
outer wall
closure flap under wall
dust flap under closure flap
inner glue seam
```

Using arbitrary epsilon offsets such as `0.001` world units is fragile when box dimensions vary. Offsets should instead derive from `boardThicknessMm` and an explicit layer index.

For technical inspection, a “separation exaggeration” option can temporarily increase those offsets to make closure construction visible. Presentation mode should use physically small offsets.

## Lighting, camera, color, and post-processing

A good carton render should resemble a controlled product photograph, not a game scene. The scene needs broad reflections, a readable silhouette, soft contact grounding, and accurate artwork visibility.

### Recommended studio lighting rig

The most effective baseline is:

```text
Environment light
    + broad key light
    + weaker fill light
    + optional rim light
    + shadow-catching floor
```

Three.js provides `RoomEnvironment`, which can be converted through `PMREMGenerator` and used as image-based lighting for PBR materials. `PMREMGenerator` prefilters environment lighting according to material roughness and the GGX model used by Three.js PBR materials. citeturn2search2turn2search5

A suitable initial configuration is:

```ts
const room = new RoomEnvironment();
const pmrem = new THREE.PMREMGenerator(renderer);
scene.environment = pmrem.fromScene(room).texture;
```

The environment should create the primary broad reflections. A directional or rectangular key light can then give the user visible control over lighting direction and shadow character. Avoid filling the scene with several point lights: point lights radiate in all directions and use inverse-square attenuation, which is less representative of large studio softboxes. citeturn8search19

### User-facing lighting model

The interface should not expose Three.js implementation details. It should expose packaging-photography concepts:

| Control | Internal behavior |
|---|---|
| Light direction | Azimuth and elevation of key light |
| Brightness | Key intensity or exposure-adjusted intensity |
| Softness | Light radius, shadow radius, or VSM blur parameters |
| Fill | Environment intensity or secondary fill intensity |
| Rim | Optional rear-side highlight |
| Shadow strength | Shadow material opacity or shadow contribution |
| Shadow softness | Key size or shadow filtering |
| Floor distance | Vertical relationship between carton and receiver |

The Appsforlife controls demonstrate that camera, direct lighting, object lighting, and floor shadow can be understandable without exposing shader language. Its “Horizontal,” “Vertical,” “Blur,” “Direct,” and “Ambient” model is worth adapting, although CartonBuilder should add presets to reduce the number of sliders shown initially. citeturn1view2

### Shadow strategy

A transparent `ShadowMaterial` floor is appropriate for transparent PNG export because it can receive a shadow while remaining otherwise invisible. citeturn8search1

Recommended shadow modes are:

| Mode | Implementation | Purpose |
|---|---|---|
| **Off** | No receiver or shadow map | Technical inspection |
| **Contact** | Transparent floor plus soft shadow | Transparent PNG |
| **Studio floor** | Visible neutral floor plus shadow | Catalogue render |
| **Ambient grounding** | Contact shadow plus GTAO | Strongest realism |
| **Fast** | Simplified shadow mesh or blob shadow | Low-end device fallback |

Three.js provides GTAO for higher-quality ambient occlusion, while explicitly noting that it is more expensive than SSAO. GTAO is useful around flap overlaps, wall intersections, and the floor contact region, but it should be enabled only in Presentation mode or during final still rendering. citeturn8search3turn8search17

Shadow maps should not update continuously if neither the carton, key light, nor floor changes. Three.js allows shadow auto-updates to be disabled and refreshed only when required. citeturn7search1turn8search11

### Camera design

A perspective camera is appropriate for presentation because it mimics normal visual perspective. Three.js supports direct focal-length control based on a 35 mm film gauge, which is more intuitive for photography presets than exposing raw field-of-view degrees. citeturn7search0

Recommended presets:

| Preset | Suggested visual character |
|---|---|
| **Technical** | Long focal length, weak perspective distortion |
| **Catalogue** | Approximately normal-lens perspective |
| **Hero** | Slightly wider perspective and lower camera position |
| **Front** | Nearly orthographic front-facing inspection |
| **Isometric** | Balanced three-face visibility |
| **Top detail** | Close top-panel or closure view |

An orthographic camera should remain available for technical inspection because object size does not change with camera distance. It is not the best default for marketing renders, but it is useful for comparing panel alignment and avoiding misleading perspective. citeturn7search2

Instead of exposing “Perspective” as an abstract slider, CartonBuilder can show:

```text
Lens: Technical / 70 mm / 50 mm / 35 mm / Custom
```

A longer focal length creates flatter-looking perspective; a shorter focal length increases depth exaggeration. The preset should move the camera as necessary so the carton continues to fill the frame.

### Depth of field

Depth of field should be disabled by default. It can make a hero render attractive, but it also hides small pharmaceutical text and can undermine artwork inspection.

Three.js provides `BokehPass` for rasterized depth of field. The path-tracing library discussed later also supports physical camera properties such as focus distance and f-stop. citeturn8search2turn11view0

Recommended product behavior:

- Technical mode: always sharp.
- Catalogue preset: always sharp.
- Hero preset: optional subtle depth of field.
- Close-up preset: focus point selectable by clicking a panel.
- Export dialog: warn when text-bearing panels fall outside the sharp focus range.

### Tone mapping and output color

Three.js renderers output sRGB by default, while tone mapping is configurable and defaults to no tone mapping. Available algorithms include ACES Filmic, AgX, Neutral, and others. citeturn2search3turn2search13

For CartonBuilder, **Neutral** or **AgX** should be evaluated first for artwork-sensitive presentation renders; ACES Filmic can produce an attractive photographic result but may alter saturated packaging colors more noticeably. The final choice should be validated with a fixed set of artwork test files rather than selected only by visual preference.

When using `EffectComposer`, the chain should finish with `OutputPass`, because it performs tone mapping and color-space conversion according to renderer settings. SMAA must be placed before `OutputPass` because it operates in linear sRGB. citeturn2search11turn8search0

A suitable WebGL post-processing order is:

```text
Scene render
→ optional GTAO
→ optional depth of field
→ SMAA
→ OutputPass
```

Do not add bloom, chromatic aberration, strong vignette, film grain, or aggressive sharpening to the default packaging workflow. Those effects may look cinematic but can degrade artwork legibility and trust.

### Color-management limits

Browser canvas and WebGL now expose sRGB and Display P3 output options on supported systems, but they do not provide a general browser-native CMYK rendering pipeline equivalent to professional prepress software. Canvas context settings are centred on sRGB and Display P3, and WebGL drawing-buffer and texture-import color-space controls likewise expose those RGB spaces. citeturn9search0turn9search4turn9search10

The product should therefore state clearly:

> **The 3D preview is an RGB visual simulation, not a contract color proof.**

This is especially important for pharmaceutical artwork, spot colors, metallic inks, overprint, and substrate-dependent results. Appsforlife similarly distinguishes browser mockups from its professional workflow supporting CMYK, color profiles, spot colors, and high-resolution CPU/GPU rendering. citeturn1view2turn0search1

Display P3 may be offered as an experimental presentation output when supported, but sRGB should remain the interoperable default for downloaded PNG and JPG files.

## Rendering performance, compatibility, and export

The carton scene is geometrically simple, but uploaded artwork can be large and export resolution can be expensive. Performance work should focus on textures, post-processing, pixel count, resource lifecycle, and unnecessary frame rendering—not polygon reduction.

### Render on demand

The application should not run a full 60 FPS loop while the carton and camera are stationary.

Render only when one of these changes:

- fold progress;
- camera;
- canvas size;
- artwork;
- material;
- light;
- background;
- selected-panel highlight;
- presentation settings.

During active orbiting or folding, render continuously. After interaction stops, render one or several final refinement frames and then suspend the loop.

This approach reduces CPU/GPU use, battery drain, and fan activity without changing visual quality.

### Adaptive rendering resolution

Three.js warns against uncritically rendering every heavy scene at full device pixel ratio. High-density displays can multiply fragment-processing cost substantially. citeturn5search20

Use a quality controller:

```ts
const interactivePixelRatio = Math.min(
  window.devicePixelRatio,
  deviceTier === 'low' ? 1 : deviceTier === 'medium' ? 1.5 : 2
);
```

A better long-term implementation measures moving frame time:

```text
If frame time > 33 ms for several frames:
    reduce render scale

If frame time < 14 ms for a sustained period:
    increase render scale gradually
```

Only the drawing buffer should be reduced. UI text, property panels, and the 2D editor should stay at normal browser resolution.

### Quality tiers

| Feature | Fast | Balanced | High | Still export |
|---|---:|---:|---:|---:|
| Render scale | 0.75 | 1.0 | 1.0–1.5 | Explicit output size |
| Artwork texture | 1K | 2K | 4K where supported | Capability-based |
| Shadows | Basic/contact | Soft | Soft high-resolution | Highest safe resolution |
| Environment | Low resolution | PMREM studio | PMREM studio | PMREM or path-traced |
| GTAO | Off | Optional low-res | On | On |
| Depth of field | Off | Off | Optional | Optional |
| Anti-aliasing | MSAA/FXAA | SMAA | SMAA | SMAA or SSAA |
| Path tracing | Off | Off | Off | Optional |

Three.js supplies SMAA for higher-quality edge anti-aliasing and a supersampling node that produces very high quality by rendering the scene repeatedly with camera jitter, while warning that SSAA is extremely expensive. SSAA therefore belongs in still export, not ordinary interaction. citeturn8search0turn8search15

### High-resolution still export

Do not rely on `preserveDrawingBuffer: true` for ordinary rendering merely to support download. The default is false, and a dedicated render target is a cleaner export path. Three.js supports offscreen render targets and asynchronous pixel readback through `readRenderTargetPixelsAsync()`. citeturn7search1turn7search9

Recommended export process:

1. save the current interactive canvas and camera state;
2. allocate a dedicated render target at the requested output dimensions;
3. render the presentation scene using export-quality settings;
4. read pixels asynchronously;
5. flip the WebGL row order;
6. encode through `OffscreenCanvas` or a temporary canvas;
7. restore interactive settings;
8. dispose the temporary render target.

For extremely large output, `PerspectiveCamera.setViewOffset()` can divide a larger camera frustum into tiles. This allows a high-resolution image to be rendered in sections instead of allocating one enormous render target. citeturn7search0

Suggested export sizes:

```text
Preview        1280 × 1280
Presentation   2048 × 2048
High quality   4096 × 4096
Custom         constrained by GPU capability and memory estimate
```

Landscape and portrait ratios should also be supported. The image dimension, not a nominal DPI label, is what matters for a screen-oriented 3D mockup.

### Transparent background

Transparent PNG export requires more than clearing the canvas alpha. The implementation must decide whether the floor shadow is retained:

| Export option | Background | Shadow |
|---|---|---|
| Transparent object only | Alpha | None |
| Transparent with shadow | Alpha | Shadow catcher retained |
| White studio | White | Visible |
| Custom studio | Color/gradient | Visible |

Appsforlife’s transparent-background option is an important usability precedent. CartonBuilder should make “Transparent with shadow” the recommended default because an isolated box without grounding can appear to float. citeturn1view2turn8search1

### Progressive path-traced stills

The closest open browser-side architecture to the Appsforlife experience is a raster preview followed by progressive path-traced accumulation after interaction ends.

The `three-gpu-pathtracer` project uses WebGL 2 and `three-mesh-bvh` for GPU path tracing. It supports the GGX surface model, standard and physical Three.js materials, textures, normal maps, environment maps, depth of field, area lights, tiled rendering, progressive samples, a low-resolution dynamic preview, and a rasterized preview while the high-quality result converges. citeturn11view0

Its API includes several capabilities directly relevant to CartonBuilder:

- `renderSample()` accumulates progressive samples;
- `reset()` restarts after scene or camera changes;
- tiled rendering improves page responsiveness;
- `dynamicLowRes` can show an immediate low-resolution image;
- `rasterizeScene` keeps the normal scene visible during convergence;
- `samples` exposes progress;
- physical camera settings support focus distance and f-stop;
- matte objects allow compositing-oriented workflows. citeturn11view0

However, the project also documents important constraints: it requires WebGL 2, supports only standard and physical materials, requires compatible texture settings, and does not support every geometry arrangement. It is a community dependency rather than a core Three.js renderer. citeturn11view0

The right integration is therefore:

```text
Interactive movement
    → realtime raster renderer

Camera becomes idle
    → optionally prepare path-tracing scene
    → render progressive samples
    → show quality/progress indicator

Any camera, material, artwork, fold, or light change
    → cancel/reset accumulation
    → return immediately to raster preview
```

Path tracing should initially be enabled only for the fully folded, static presentation scene. Supporting animated folds inside the path tracer adds scene-update cost without providing meaningful benefit.

A reasonable first experiment is a “High-quality render” button rather than automatic path tracing. This limits dependency risk and allows real device measurements before making it part of the default workflow.

### Image decoding and worker pipeline

Uploaded artwork should be decoded with `createImageBitmap()` and, when resizing or raster compositing is needed, processed through `OffscreenCanvas`. `ImageBitmap` is designed as an efficient image object suitable for transfer and texture preparation, and retired bitmaps should be closed explicitly. fileciteturn0file0

The pipeline should produce at least two derived assets:

```text
Artwork original
    ├── technical/export representation
    └── 3D preview bitmap
            ├── mobile resolution
            └── desktop/high-quality resolution
```

Replacing artwork should cancel pending decodes, dispose the old GPU texture, close superseded bitmaps, and remove stale worker results by generation ID.

### Memory and context loss

Three.js textures cannot safely change dimensions, format, or type after first use; replacement requires disposal and recreation. Renderer statistics expose active texture and geometry counts for diagnostics. citeturn2search15turn10search9

CartonBuilder’s Diagnostics dialog should display:

```text
Renderer backend
GPU vendor/renderer where available
Canvas drawing-buffer size
Pixel ratio/render scale
Maximum texture size
Artwork source size
Artwork preview texture size
Active textures
Active geometries
Draw calls
Triangles
Shadow-map size
Post-processing passes
Estimated export allocation
```

WebGL contexts can be lost because of GPU pressure, GPU switching, driver reset, or other system events. After restoration, textures and buffers created before context loss are no longer valid and must be recreated. The browser extension for deliberate context loss should be used in automated resilience testing. citeturn10search0turn10search3turn10search15

## Product UX, validation, and competitor lessons

Technical and presentation settings should not be mixed into one unstructured panel. Users validating artwork orientation should not need to understand aperture or shadow blur, while users creating a mockup should not be distracted by fold-line overlays.

### Presets before sliders

A small set of tested presets should produce good results immediately:

| Preset | Intended output |
|---|---|
| **Technical White** | Neutral, sharp, minimal perspective, dieline optional |
| **Clean Studio** | White background, soft key, modest contact shadow |
| **Catalogue** | Neutral light, full sharpness, consistent camera |
| **Soft Grey** | Light-grey sweep, gentle shadow, broad reflection |
| **Hero** | More directional light, subtle rim, optional depth of field |
| **Transparent** | Alpha background with retained contact shadow |
| **Flat Artwork Check** | Minimal reflections and maximum artwork readability |

Advanced controls can be revealed after the preset is selected. Every preset should be stored as data and versioned, not implemented as scattered UI constants.

### Lessons from Appsforlife

The competitor’s strongest ideas are:

- one-click image download;
- explicit transparent-background control;
- understandable camera controls;
- separate direct and ambient lighting;
- separate object and floor-shadow treatment;
- visible progressive-render quality indication;
- automatic restart when rendering parameters change. citeturn1view2

Its weakest ideas for CartonBuilder’s use case are:

- separate artwork uploads by visible side;
- duplicated opposite-panel artwork;
- no authoritative dieline relationship;
- mockup dimensions inferred from artwork rather than structural data;
- a static-output-first workflow that does not prioritise production verification. citeturn1view2

CartonBuilder should reproduce the simplicity of the first group while explicitly rejecting the structural shortcuts of the second.

### Trust and technical status

Presentation mode must never imply that the render is a print-production colour proof. The exported render metadata or download dialog should show:

```text
Rendering intent: Presentation mockup
Output color space: sRGB
Technical scale: Not applicable
Artwork source: [filename]
Carton dimensions: W × H × D mm
Material simulation: [preset]
```

Technical exports should retain their separate proof statement about 1:1 geometry and PDF/X status, as the current application already does. citeturn1view0

### Rendering tests

A visual rendering test suite should contain fixed reference projects rather than only generic cubes.

Recommended fixtures include:

| Fixture | Detects |
|---|---|
| White carton with black text | Blur, anti-aliasing, text legibility |
| Saturated cyan/magenta/yellow artwork | Tone-mapping and color-space shifts |
| Artwork crossing two folds | UV continuity and seam bleeding |
| Thin barcode on side panel | anisotropic blur and texture resolution |
| Open box with visible inside | front/back material correctness |
| Reverse-tuck closure | flap order and z-fighting |
| Gloss-varnish mask | clearcoat alignment |
| Metallic-foil patch | metalness-mask alignment |
| Transparent PNG with shadow | alpha and premultiplication defects |
| Large portrait carton | camera-fit and shadow-frustum issues |

Visual comparisons should be generated at fixed renderer version, browser version, camera, exposure, and output resolution. Mathematical tests should independently verify UV coordinates, fold transforms, panel-local normals, board-thickness offsets, and camera framing.

The test matrix should include Chrome, Edge, Firefox, and Safari-class browsers where possible, plus integrated-GPU laptops and representative mobile devices. WebGPU must remain a feature-tested enhancement because the underlying browser API is not yet universally available, even though Three.js can fall back to WebGL 2 through `WebGPURenderer`. citeturn5search0turn5search4

## Delivery roadmap and acceptance criteria

### Immediate rendering foundation

This phase should improve quality without changing the project model fundamentally.

| Work item | Priority | Expected value |
|---|---:|---|
| Renderer adapter interface | Critical | Prevents lock-in and enables WebGPU/path-tracer experiments |
| Separate Technical and Presentation modes | Critical | Establishes correct product model |
| Proper sRGB artwork texture configuration | Critical | Prevents avoidable color errors |
| PMREM studio environment | High | Immediate improvement to PBR readability |
| Soft key light and shadow catcher | High | Grounded, product-photography appearance |
| Camera presets and Fit Object | High | Faster, repeatable output |
| Transparent PNG with optional shadow | High | Direct presentation value |
| Dedicated high-resolution render target | High | Reliable export without compromising interactive renderer |
| Resource-disposal audit | High | Prevents repeated-upload memory growth |

Acceptance criteria:

- The 2D artwork placement and 3D UV mapping remain pixel-consistent at every fold position.
- Presentation settings do not modify canonical artwork placement or dieline geometry.
- Replacing artwork repeatedly does not cause continually increasing active texture counts.
- Transparent PNG preserves clean alpha edges.
- Camera presets frame cartons across a documented range of dimensions.
- Technical 3D remains available if optional presentation effects fail.

### Realistic carton construction

This phase adds the visual cues that make the box feel physical.

| Work item | Priority | Expected value |
|---|---:|---|
| Board thickness in canonical model | Critical | Foundation for realistic edges and overlaps |
| Separate outside and inside surfaces | High | Correct open-flap rendering |
| Edge-strip material | High | Strong silhouette improvement |
| Thickness-based flap offsets | High | Removes z-fighting |
| Small presentation bevel | Medium | Produces edge highlights |
| Crease shading | Medium | Communicates folded paperboard |
| Coated and uncoated board presets | High | Useful default materials |
| Gloss/matte/spot varnish presets | Medium | Packaging-specific differentiation |
| Foil and emboss preview layers | Later | Advanced artwork-finish simulation |

Acceptance criteria:

- Open cartons show a distinct internal board material.
- Edge thickness remains visually stable at close and distant camera positions.
- Fully closed flaps do not flicker or occupy identical depth.
- Technical mode can disable thickness exaggeration and presentation bevels.
- Material masks remain aligned through all fold transformations.

### Enhanced presentation pipeline

| Work item | Priority | Expected value |
|---|---:|---|
| GTAO in high-quality mode | Medium | Better grounding and flap depth |
| SMAA and correct OutputPass ordering | High | Cleaner text and edges |

Acceptance criteria:

- Balanced interactive mode remains responsive on the agreed reference laptop.
- Final still export does not inherit reduced interactive render scale.
- Depth of field is disabled by default and never affects Technical 3D.
- Post-processing preserves transparent export correctly.
- Tone-mapping choice is validated against the fixed saturated-artwork fixtures.

### Progressive renderer experiment

The experiment should be time-boxed and judged by measurable product value.

Prototype scope:

```text
One fully folded carton
One studio environment
One area/key light
Standard and physical carton materials
Transparent and studio backgrounds
Progress indicator
Cancellation and restart
2048 px output
```

Success criteria:

- Raster preview appears immediately.
- Camera movement remains responsive.
- Accumulation resets reliably after every scene-changing action.
- A visibly cleaner render is produced within an acceptable wait on the reference device.
- Textures, materials, transparency, clearcoat, and normal maps match the raster version closely.
- Failure or unsupported hardware falls back cleanly to enhanced raster export.

The experiment should be rejected or postponed if path tracing significantly increases bundle size, causes frequent device failures, produces inconsistent material interpretation, or requires maintaining two divergent material systems. Enhanced raster rendering with correct geometry, PMREM lighting, soft shadows, PBR materials, anti-aliasing, and high-resolution export will already deliver most of the visual improvement users perceive.

### Recommended final architecture

```text
CartonBuilder canonical model
    ├── millimeter-native dieline
    ├── artwork placement
    ├── hinge graph
    ├── board thickness
    ├── material/finish metadata
    └── presentation preset

Technical 3D renderer
    ├── fast raster
    ├── fold inspection
    ├── panel selection
    ├── labels and dieline
    └── always available

Presentation 3D renderer
    ├── solid panel geometry
    ├── PBR carton materials
    ├── PMREM studio lighting
    ├── soft shadows and GTAO
    ├── camera presets
    ├── SMAA and tone mapping
    └── high-resolution PNG/JPG export

Optional still-quality renderer
    ├── progressive samples
    ├── raster preview during convergence
    ├── depth of field
    ├── transparent compositing
    └── explicit user-triggered export
```

The decisive best practice for CartonBuilder is not “use path tracing.” It is to build a disciplined rendering pipeline in the correct order:

> **authoritative flat geometry → stable UV mapping → physically plausible thickness → correct color-space handling → PBR materials → studio lighting → soft grounding → restrained post-processing → dedicated high-resolution export → optional progressive refinement.**

That sequence will produce a larger and more reliable quality gain than beginning with an expensive renderer while the carton remains a set of infinitely thin, uniformly lit planes.
