# CartonBuilder Presentation Render Runtime

Status: Implemented
Version: 7
Last verified: 2026-08-03
Canonical for: the Presentation Render step, its persisted settings and image/3D export

This document describes the implemented fourth workflow step, **Render**. It
complements the technical Preview specification: Preview is for inspecting the
fold graph and dieline; Render is for producing a reproducible closed-carton
presentation image.

## Workflow and state ownership

Render is enabled only when the BoxNet model is complete and at least one visible
artwork entry is available. Preview is suspended while Render is active. The two
surfaces own separate Three.js scenes, so orbit, fold progress, selections, and
GPU resources are not shared mutable state.

Render always constructs its scene with `foldProgress = 1`. Returning to Preview
does not alter its technical fold, camera, or scene preset.

The canonical sources remain `BoxNetModel` and `ArtworkModel[]`. Render derives a
`RenderSceneModel` and uses the same flat-net artwork composition as Preview:
visible entries only, original layer order, crop, rotation, opacity, PDF-layer
visibility, and panel UV continuity are preserved. Render never writes back to
artwork or box geometry.

## Camera and preset workflow

The Render camera exposes deterministic built-ins (`front`, `back`, `left`,
`right`, `top`, `bottom`, `front-left`, `front-right`, `top-front`, and
`isometric`) with stable up vectors for the top and bottom views. Perspective
FOV is canonical; 35/50/85 mm lens choices use a fixed 24 mm full-frame sensor
height and derive FOV without changing the camera target. Orthographic framing
stores `orthographicHeight`. `Fit` preserves the current direction, projection,
and lens while clearing pan; `Reset` reapplies the active View Preset or falls
back to the isometric built-in. Perspective-only `verticalCorrection` uses an
off-axis projection shift to keep vertical carton edges parallel.

View Presets are global IndexedDB records in `renderViewPresets`, separate from
the legacy Preview `scenePresets`. They store normalized heading/elevation,
pan, distance/frame factors, projection, FOV, and correction; exact position and
target remain project state. Missing global presets never erase the project
camera and are displayed as Custom. Render Presets are full deterministic
snapshots of Render/Export/Camera/Board state, while Artwork quality is excluded
from both preset types. User presets are editable/duplicable; built-ins are
read-only. Thumbnail records live in the separate `presetThumbnails` store and
are generated from a neutral carton through the real renderer.

## Persisted settings

`src/render/RenderSettings.js` defines the defaults and sanitizes every value
before it reaches the renderer, browser storage, or project snapshot. Unknown
enums fall back to defaults, numbers are clamped, vectors must contain finite
values, and colors must be six-digit hex values. The legacy long-edge presets
remain 2048/4096; the export dialog also supports bounded custom pixels and
print sizing in cm or inches with an explicit PPI.

Schema version 10 adds the following project fields:

```js
{
  render: {
    presetId, aspect, longEdge, camera, activeViewPresetId, viewPresetBaseId,
    background, lighting, shadows, floor, material, quality, output, effects
  },
  artworks: [{
    outputRole: 'print' | 'finish' | 'print-and-finish',
    finish: null | {
      type: 'spot-gloss' | 'foil' | 'emboss' | 'deboss',
      maskChannel: 'auto' | 'alpha' | 'luminance',
      invert, intensity, foilColor, foilRoughness, reliefStrength
    }
  }],
  renderAppearance: { thicknessMm, bevelRadiusMm, interiorColor, edgeColor }
}
```

The v2 → v10 migrations inject sanitized defaults and do not change artwork,
box, history, or existing view state. Board appearance is included in the
optional `renderAppearance` project field and is also saved with the Render
settings. Transient renderer information, GPU handles, export progress, and
diagnostics are never serialized. Named presets are presentation presets; the
project stores the currently applied basic/effects settings.

All Render settings and board appearance are written synchronously to
`cartonBuilder.renderSettings.v1`, so a page reload does not depend on the
500 ms autosave debounce. The project snapshot remains authoritative when an
autosave or `.carton` file is restored; browser storage is the immediate
startup fallback. The current project schema is version 10 and retains backward
compatibility for older projects and v2 `.carton` archives. Archive format v3
stores embedded Render background images under `render-assets/`, addressed by
SHA-256 asset ID, so projects do not depend on external paths.

The Render UI keeps the viewport between two independently scrollable settings
panels. The left panel groups output controls (Render/View preset galleries,
artwork quality, camera, frame, material and board appearance); the right panel groups lighting, background,
shadows, effects and diagnostics. At narrow widths the viewport comes first and
the two panels stack below it.

The default Clean Studio baseline is calibrated for color-sensitive packaging
visualization: Neutral tone mapping and sRGB output are paired with a restrained
studio environment (`0.40`), key light (`1.7`) and exposure (`0.85`). A neutral
grey background (`#d9dcde`), soft shadow and compact GTAO preserve white-board
edge separation without washing out the printed artwork. The named Catalogue,
Soft Grey and Transparent presets use the same highlight-safe lighting policy.
Floor reflection is off by default; Catalogue enables a restrained world-space
reflection for glossy presentation. Reflection and shadow inclusion in
transparent PNG are opt-in independently.

## Packaging finishes and mask pipeline

Artwork entries can opt into a finish role from the existing artwork layer. The
role `print` keeps the layer in the printed base texture, `finish` uses the
layer only as a mask, and `print-and-finish` does both. Finish-only layers are
excluded from technical SVG/PDF output and from the ordinary 2D proof, while
remaining available in Render and presentation exports. The mask source is
auto-detected from alpha or can be forced to luminance; inversion and a
normalized intensity are persisted with the project.

Render composes masks in the same flat-net UV canvas as the artwork. Spot gloss
drives clearcoat and clearcoat roughness, foil drives metalness, roughness and a
selectable foil tint, and emboss/deboss produce a signed height field plus a
tangent-space normal map. The generated base-color, clearcoat,
clearcoat-roughness, metalness, roughness and normal maps are data maps with
explicit non-color encoding and are replaced/disposed atomically with the
artwork texture. This is a presentation approximation, not a certified
varnish, foil or emboss production separation.

## Renderer contract

`WebGLCartonRenderer` is the presentation adapter behind the Render controller.
It uses the existing procedural panel geometry and fold graph, but creates its
own `WebGLRenderer` with alpha support, sRGB output, a PBR board material, one
directional shadow light, a RoomEnvironment PMREM, and a ground/contact shadow
receiver. An optional planar world-space reflector shares the floor coordinate
system and is resized with the carton bounds. A true 2D backplate is rendered
as an unlit camera-facing texture with exact cover/contain crop, so lighting
cannot wash out the supplied background. Uncoated and Matte use
`MeshStandardMaterial` without finish maps; Gloss and any finish-mapped surface
use `MeshPhysicalMaterial` so clearcoat, foil and relief inputs remain active.

The Preview scene remains intentionally flat and technical. Render uses solid
presentation panels with thickness/bevel, interior/edge material groups, and
the independent quality states `interactive → settled → export`. Interactive
uses SMAA/native raster; settled/export can enable GTAO, TAA, and explicit DOF.
`OutputPass` is the final color-conversion pass. WebGPU is not used, and path
tracing is a disabled-by-default gated experiment.

## Still export

`StillRenderService` calculates the exact frame dimensions:

| Aspect | 2048 | 4096 |
| --- | --- | --- |
| 1:1 | 2048×2048 | 4096×4096 |
| 4:3 | 2048×1536 | 4096×3072 |
| 16:9 | 2048×1152 | 4096×2304 |
| 3:4 | 1536×2048 | 3072×4096 |

The service renders to a temporary `WebGLRenderTarget`, reads pixels
asynchronously when supported, flips WebGL rows, and encodes through
`OffscreenCanvas` or a temporary DOM canvas. It does not set
`preserveDrawingBuffer: true`. JPEG is encoded at the selected output quality
(default 0.94) and is always
composited on an opaque background. PNG supports transparent object-only output
or a transparent shadow catcher. Render targets and temporary resources are
disposed in `finally` blocks.

Each export accepts an `AbortSignal`. Starting a new export, replacing artwork,
changing Render settings, resetting the project, or losing the graphics context
cancels stale work. A stale promise cannot publish an old download.

Output names use the box dimensions and applied preset:

```text
carton-render-{width}x{height}x{depth}mm-{presetId}-{longEdge}.png
carton-render-{width}x{height}x{depth}mm-{presetId}-{longEdge}.jpg
```

Before allocation the service compares the target against reported texture and
renderbuffer limits. If the device cannot allocate 4096, the UI reports a clear
GPU-limit error and the user can select 2048.

## Export preflight, health and lifecycle

The Export dialog runs `runRenderExportPreflight` for Image, Turntable sequence
and Binary glTF before allocation. It reports `ready`, `warning` or `blocked`.
GPU-limit, lost-context and turntable pixel-budget errors block the Export
button. JPEG transparency and Basic GLB finish simplification are warnings and
can be acknowledged. The preflight estimate is advisory and is not persisted.

`WebGLCartonRenderer.getDiagnostics()` exposes backend/context state, recovery
count, drawing-buffer and GPU limits, render passes, resource counters, quality
frame-time statistics, health status and the last still-export duration. The
Settings diagnostics download may include this sanitized Render snapshot but
never includes artwork bytes, file names, GPU vendor data or project IDs.

`RenderApp.whenStable()` waits for pending scene synchronization and two settled
animation frames, then activates the settled post-processing state. Artwork
quality changes, finish-map replacement, exports and context restoration are
generation-safe; stale work cannot publish an old texture or download. PMREM
render targets and temporary finish textures are disposed after replacement.

## Unified 3D export

The Render export dialog uses one output contract for Image, Turntable sequence,
and Binary glTF. Image keeps the exact still-export behaviour above. Turntable
uses 24, 36, or 72 frames (36 by default), a 512/1024/2048 px long edge (1024
by default), PNG/JPG encoding (PNG by default), evenly spaced heading samples,
`frame-001` naming and no duplicate 360-degree frame. A 160-megapixel total
pixel budget prevents accidental browser allocations. The service accepts an
`AbortSignal`, reports progress, and restores the original camera in `finally`.

Binary glTF is a static closed-carton export. The export-owned scene is Y-up,
converts source millimetres to metres at the root, carries exterior/interior/
edge surfaces and embeds artwork textures. Full PBR preserves the generated
finish maps and physical board material; Basic Compatibility downgrades to
`MeshStandardMaterial` and intentionally simplifies clearcoat, foil and relief
for viewers with limited `KHR_materials_*` support. When active finishes exist,
the export dialog shows this limitation before export. The current camera is
included by default. Render-only floor, backplate, environment, shadow catcher
and post-processing are deliberately omitted so the asset remains portable.
The file name includes dimensions and the selected material profile.

## Color and production boundaries

Artwork textures are treated as sRGB and material/data maps as non-color data.
The Render surface is an sRGB presentation visualization; it is not CMYK,
ICC/Pantone, overprint, trapping, or certified varnish/foil/emboss production
separation validation. Technical SVG/PDF output remains the production-oriented dieline
workflow.

## Test coverage

Unit coverage validates settings/effects and finish sanitization, background asset checksums
and frame dimensions,
deterministic presets, board appearance and solid geometry, postprocessing pass
plans, quality state transitions, closed Render scene construction without
canonical-state mutation, offscreen PNG/JPG options, GPU limits, abort handling,
and v2 → v10 migration. Browser coverage also verifies deterministic
studio/transparent baselines, image backplate, reflection toggle, export sizing
dialog, GPU-limit blocking, context loss/recovery and bounded resource counters
across repeated refreshes.
Browser coverage validates the disabled stepper state, Preview → Render
navigation, closed-scene isolation, settings persistence in the active session,
finish-only layer exclusion from technical output, and real PNG, validated GLB
and numbered turntable ZIP exports. GLB tests check
the binary header and Khronos validator errors; ZIP tests check frame count,
names and camera restoration.

## Deferred milestones

Collision simulation, production valve mechanics, CMYK/ICC/Pantone proofing,
WebGPU, and production path tracing remain deferred. Visual baselines use a
fixed Chromium/SwiftShader capture environment and are not print-proof
validation. The path-tracing adapter
is only loaded when `VITE_ENABLE_RENDER_PATH_TRACING=true` and an explicitly
compatible optional dependency is installed.
